## Current Implementation Status

The system now uses **New Age Bangladesh** as the live data source for road accident news.

Current source configuration:

- Source name: `New Age`
- Listing URL: `https://www.newagebd.net/tags/accident`
- Pagination range: `page=1` to `page=16`

The original architecture is preserved:

- Article pages are scraped and stored in the `articles` table.
- OpenAI-based structured extraction reads `articles.content`.
- Extracted concrete accident events are stored in the `accidents` table.
- Non-incident/report/editorial/null LLM events are discarded before accident insert and logged to `data/non_incident_report.log`.
- Fresh scrapes now store the correct article-specific published date from New Age article pages.
- `accidents.accident_date` continues to inherit `articles.published_date`.
- The UI continues reading from the same DB-backed APIs.
- The DB schema, UI contract, and LLM integration style remain unchanged.

## Current Workflow

1. Scraper loads New Age accident tag pages.
2. It collects article links from each page.
3. Each article page is visited and parsed for:
   - `url`
   - `title`
   - `content`
   - `published_date` from the article header/byline area
4. Raw article data is inserted into `articles`.
5. The OpenAI extraction pipeline processes the article content using a strict JSON schema.
6. Backend normalization and filtering are applied.
7. Concrete accident rows are inserted into `accidents`; discarded non-incident events are logged to `data/non_incident_report.log`.
8. Dashboard and analytics APIs read from the resulting SQLite data.

## Enforced Constraints and Guardrails

- `accident_date` is always taken from `articles.published_date`.
- `published_date` is extracted from the article-specific publish timestamp, not from generic page-level dates.
- LLM-provided event dates are ignored during DB insert.
- District values must resolve to backend-supported districts or be stored as `null`.
- Locality names such as `Uttara`, `Mirpur`, `Savar`, and `Tongi` are normalized through `normalize.py`.
- Coordinates are never generated by the LLM.
- Latitude and longitude are assigned only from backend mappings in `geo.py`.
- Historical or aggregate report-style items are filtered before insertion.
- Non-incident, editorial, empty/null, and no-concrete-incident LLM events are filtered before insertion.
- Discarded LLM events are logged as newline-delimited JSON in `data/non_incident_report.log`.
- Casualty sanity limits are enforced before insert.
- One article can produce multiple accident rows.
- Existing article URLs are skipped because `articles.url` is unique.

## Current Setup Details

- Scraping is implemented with `requests` and `BeautifulSoup`.
- API server is `FastAPI`.
- Storage is `SQLite`.
- Extraction uses OpenAI Chat Completions with strict JSON schema validation through Pydantic.
- Scheduler runs periodic scraping using APScheduler.
- Raw LLM responses and failures are logged under `data/`.

## Known Limitations

- Aggregate, historical, and non-incident filtering is heuristic, not perfect.
- Reprocessing articles can create duplicate rows in `accidents`.
- Deduplication exists for article URLs, not for extracted accident events.
- Published date parsing depends on New Age article markup and selector stability.
- The canonical date policy uses article publish date, which may differ from the actual event date mentioned in the report.
- Scraper correctness depends on New Age page structure and selectors.
- There is no dedicated automated test suite yet.

## Current Filtering Limits and Edge-Case Risks

The current implementation already does two useful things:

- The LLM prompt tells the model to return only concrete accident incidents.
- Backend guardrails try to reject aggregate or historical records before DB insertion.

However, the current setup is still limited because aggregate/report rejection is not fully model-driven and is not fully article-aware. The backend rejection logic depends mainly on extracted event fields such as `summary`, `location_raw`, and `accident_type`, not on the entire article title and full article body. Because of that, some report-style stories can still slip through if the LLM returns a neutral-looking summary.

Possible failure cases in the current setup:

- Report-style headlines may still be treated as incident news if the model output does not preserve words such as `report`, `survey`, or `statistics`.
- Historical or monthly summary stories with realistic-looking casualty counts may bypass casualty sanity limits.
- Title-driven cues can be lost when the model compresses the article into a short summary.
- Borderline stories can be hard to separate reliably using the current prompt plus thin heuristics.

Examples already identified for exclusion:

- `Pedestrian fatalities dominate Dhaka road deaths: report`
- `Minister’s denial can’t hide road safety crisis`
- `619 people killed in road accidents across Bangladesh in March: report`
- `20 people killed daily in road accidents during Eid: report`
- `Eid-time road deaths 351`

Examples that should still be treated as valid multi-incident daily news:

- `Four killed in road accidents in Dhaka`
- `Three killed in Cox’s Bazar road accidents`
- `9 killed in road accidents in 3 districts`

Current multi-incident handling is expected to work when the article describes separate concrete incidents. In those cases, one article can create multiple rows in `accidents`, and all rows should use the same `articles.published_date` as canonical `accident_date`.

## V2 Proposal: LLM-First Article Classification

For V2, the preferred approach is to let the LLM explicitly classify the article before insertion, instead of relying primarily on hardcoded aggregate-report heuristics.

Proposed direction:

- Extend the LLM structured output to classify the article as either:
  - `daily_incident`
  - `non_incident_report`
- If the article is classified as `non_incident_report`, the LLM should return no accident records.
- If the article is classified as `daily_incident`, the LLM can return one or more accident events as it does now.
- Backend should keep only a thin guardrail layer for obvious sanity checks and malformed outputs.

Why this is preferred for V2:

- The model would make the keep/skip decision explicitly.
- Debugging would become easier because skipped articles would have a visible classification reason.
- Testing would become easier because the expected output shape is clearer.
- The system would depend less on brittle keyword-based rejection.

## Current Non-Incident Logging

Skipped LLM events are logged for manual QA.

Log file:

- `data/non_incident_report.log`

Contents:

- article id
- published date
- skip reason from backend guardrails
- event snapshot returned by the LLM

This log is intended to help QA and future tuning of false positives and false negatives while preserving the rule that skipped events do not create `accidents` rows.

## What Should Not Change Without Coordination

- Do not change the existing UI behavior or response shapes without coordinated frontend updates.
- Do not change the DB schema unless downstream consumers are updated together.
- Do not change the OpenAI extraction method from strict-schema structured extraction unless the whole validation flow is revisited.
- Do not move location resolution into the LLM; district normalization and coordinates should remain backend-controlled.

- Check `articles` contains correct `url`, `title`, `content`, and `published_date`.
- Check `accidents` rows reflect extracted deaths, injuries, district, and summary data.
- Check `accident_date` matches `articles.published_date`.
- Check article dates in DB match the published date shown on the live New Age article page.
- Check aggregate-report headlines do not create accident rows.
- Check skipped non-incident events appear in `data/non_incident_report.log`.
- Check `/api/overview`, `/api/daily`, `/api/monthly`, and `/api/map-data` still work with the current data source.
